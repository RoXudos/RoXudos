# Who it is for

## The buyer

Usually one of:

- Event director / event manager
- Event-control manager
- Operations lead at a promoter, charity, university, or local authority
- Safety officer who is tired of the spreadsheet

They buy because live control is fragmented and the risk of missing something is real.

## The daily users

| User | Main job in Livehelm |
| --- | --- |
| Event Control Manager | Owns the live picture, staffing of control, handover |
| Control Operator | Logs, incidents, tasks, programme, radio-to-system |
| Security Manager | Security incidents, deployments, ejections, posts |
| Medical Manager | Medical incidents, teams, ambulance, transfers |
| Production Manager | Programme, artists later, site issues |
| Volunteer Manager | Rotas, check-in, briefings |
| Safeguarding Lead | Restricted cases only |
| Vendor Manager | Traders, documents, pitches |
| Staff / steward / volunteer | Later: field actions. First ship: they are records, not primary users |
| Organisation Owner | Billing, org users, event creation, permissions |

## Jobs to be done

- “I need to see what is on fire right now, literally or not.”
- “I need to hand over to the next control team in ten minutes.”
- “I need a log that we can stand behind if this is investigated.”
- “I need to assign a task without starting a WhatsApp archaeology project.”
- “I need last year’s site, roles, and procedures cloned, then updated.”

## Event shapes we must not special-case in the core

The same incident, log, task, map, and programme objects must work for:

- music festivals and concerts
- Pride and parades
- charity walks/runs
- community, town, and cultural events
- Christmas markets and fireworks
- carnivals
- sport and mass participation
- corporate and university events
- public gatherings and street parties

Special features (parade order, fundraising, artist riders) are modules, not a second product.
